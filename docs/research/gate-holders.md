## 0. Registry mechanics (CONFIRMED, `PhysicsExtensions.UpdateController`)
- `SupportRigidbody(Rigidbody, float quality = 1f, ObjectVisibility visibilityChecker = null)`: only acts if `_enabled` (set by `AbstractApplication.Awake` IL 383 `UpdateController.set_Enabled` when `AppEnvironment.Config.Physics.ManualUpdate`). **Always `_rigidbodies.Add`s — no dedupe** (duplicates possible), then `CheckRigidbodiesDone()`.
- `UnsupportRigidbody(rb)`: removes only the FIRST matching entry (`RemoveAt(i); break;`), then `CheckRigidbodiesDone()`. So duplicates need N calls.
- `CheckRigidbodiesDone()` (also run every frame from `PhysicsExtensions.Update` → `UpdateController.Update`, after `Simulation.Update`): **auto-purges** entries whose `rigidbody == null` (destroyed) or `!gameObject.activeInHierarchy`. Counts entry as live if `visibilityChecker == null || visibilityChecker.IsVisible`. `Simulation.UpdateEnabled = (liveCount > 0)`.
  => An entry leaves the registry by: (a) `Destroy(rigidbody)`/`RigidbodySpawner.Remove()`, (b) GameObject inactive, (c) explicit Unsupport. Note: `isKinematic = true` / sleeping does NOT release the entry.
- Explicit `UnsupportRigidbody` callers (find_callers, complete): only `MgBelt.SetPhysicsPartsEnabled`, `CorpseRagdoll.StopRigidbody`, `HideoutArea.CG_SetupItem.MoveNext`. `ServerAirDrop` is NOT among them.
- `Simulation` mode: `UpdateController.Enabled=true` forces `UpdateMode = SmoothSimulate`, `UpdateEnabled=false` initially; `Physics.Simulate` runs only if `CanRunSimulate` (= Script sim-mode && `_updateEnabled`).

## 2. Persistent holders in an ordinary raid — does Simulate go OFF before the airdrop lands?
- **Static scene bodies** (CONFIRMED by code, scene contents UNVERIFIED): nothing in the registry is registered at scene load by scene geometry — all registrations above are code paths triggered by gameplay events or spawned prefabs. Only `WheelDrive.OnEnable` (and `RigidbodySpawner`-based prefab components) can register at scene enable, and it self-releases in ~3 s after Start. So at steady state with no activity the registry is empty → `Simulation.UpdateEnabled = false` → `Physics.Simulate` NOT called. This is also what the user's premise (airdrop is the dominant persistent holder) predicts. [INFERENCE: not runtime-verified; a runtime dump of `UpdateController._rigidbodies.Count` + `Simulation._updateEnabled` would settle it.]
- **Realistic persistent competitors**: (a) **BTR** (`VehicleSuspension.SuspensionOn`, #8) — holds the gate open from first movement to raid end on maps where the suspension is enabled: Woods and `develop`. Streets has a BTR but never enables the suspension, so it does not hold the gate; Customs and Lighthouse have no BTR in this install (`LocationsWithBTR` = `develop`, `Woods`, `TarkovStreets`; see `btr-suspension.md` §4). Where the BTR suspension is active, an airdrop fix alone will NOT turn Simulate off. (b) player-placed tripwires (#6) — not in normal raids without interaction (Fika/other players could). (c) MG belt while visible (#12). (d) uncertain: smoke grenade, SmallPhysicsObject w/ TimeOfLife=0.
- **Transient churn**: bots dying (#4/5, ≤16 s each), grenades (#2), loot drops (#3 ≤15 s), lamps hit by explosions (#9). In a busy raid Simulate flickers on for seconds at a time, then returns to off.
- **Conclusion**: in an ordinary raid on a map without a suspension-enabled BTR (anything but Woods and `develop`), Simulate is OFF between transient events, so a stuck airdrop entry is the sole persistent holder and the proposed fix has full effect. On Woods with a spawned BTR, the BTR holds it open after first movement; unsupporting `VehicleSuspension.parentBody` in `SuspensionOff` (it already sets kinematic, so physics is not needed) was implemented as `BTR/ReleaseParkedSuspension` (see `btr-suspension.md`).

## 3. Does the landed crate stay active until raid end? (CONFIRMED mostly)
`SynchronizableObjectLogicProcessor.ReturnToPool(SynchronizableObject)` (0600AF68) is the only path that deactivates a crate: it calls `_activeSynchronizableObjects.Remove`, `synchronizableObject.ReturnToPool()` (→ `ClientAirDrop.ReturnToPool` which `SetActive(false)`s the crate GO and calls `OfflineServerLogic.ReturnToPool`), then `AssetPoolObject.ReturnToPool(go)`.
Full callers of processor `ReturnToPool` (workspace scope; 3 hits):
1. `ClientSynchronizableObjectLogicProcessor.RemoveOutdatedObjects` — only for packets with `Outdated == true`. `Outdated` writers: `ServerAirDrop.UpdateOfflineClientLogic/UpdateSyncObjectData` (`Outdated = false`, constant) and `ServerPlane` (`Outdated = _isLastObjectPacket`, airplane only). So crates are never outdated.
2. `SynchronizableObjectLogicProcessor.RemoveNonActiveAndStaticObjects` (offset 154) — for objects with `IsActive == false`. Writers of `SynchronizableObject.IsActive` (find_usages): `TakeFromPool` (true) and `ReturnToPool` (false) of ServerAirDrop/ClientAirDrop/ServerPlane/ClientAirPlane/BaseTripwire, plus `TripwireSynchronizableObject.Destroyed`. For crates nothing sets `IsActive=false` except `ReturnToPool` itself ⇒ branch never fires for an airdrop.
3. `ServerPlane.CG_AwaitContainerLoot.MoveNext` (offset 261) — returns the **plane** (`serverPlane._syncObject`) to pool if `InitContainerLoot` fails; not the crate.
`ServerAirDrop.ReturnToPool` itself does not deactivate (only flags/coroutine), the deactivation is in `ClientAirDrop.ReturnToPool`.
**SPT `SPT.Custom.Patches.FixAirdropCrashPatch`** (spt-custom.dll): Harmony prefix on the `TarkovApplication` method with params `(string profileId, Profile savageProfile, LocationSettings.Location location, Result<ExitStatus,TimeSpan,ClientMetrics> result)` — i.e. the local-raid-end handler. It iterates `GameWorld.SynchronizableObjectLogicProcessor._activeSynchronizableObjects` calling `item.Logic.ReturnToPool(); item.ReturnToPool();`, then disposes `ServerAirdropManager`/processor. **Raid end only.** (It iterates only the *active* list; static crates are not touched but the processor `Dispose()` clears both lists.)
=> Proven: the landed crate stays active (and registered) from drop until raid end; nothing mid-raid deactivates/destroys it. [INFERENCE: Fika host and Fika dedicated use a different server path (`Mirror`/Fika.Core, context `adtd_fika` loaded but not inspected) — not verified.]

## 4. Can a static crate return to active / re-Init?
- **Static transition** (CONFIRMED): `ServerAirDrop.ManualUpdate` sets `_syncObject.IsStatic = true` only when `_signalFireCoroutineDone && _fallingStage == Landed`. `_signalFireCoroutineDone` is set after `SignalFireCoroutine`: waits until `HasRaycastHit(pos, SmokeActivateHeight)`, then smoke for `AirdropSettings.PlaneAirdropSmoke` seconds (unscaled), then done. So IsStatic comes smoke-duration seconds AFTER landing, not at landing. `RemoveNonActiveAndStaticObjects` (run each frame by `ClientLocalGameWorld.UpdateSynchronizableObjectLogic`, before `ManualUpdate`) then moves it to `_staticSynchronizableObjects`; `ManualUpdate` loops only the active list ⇒ **ServerAirDrop.ManualUpdate stops being called after that**. A postfix on `ManualUpdate` that checks `IsStatic` therefore fires on the same frame IsStatic flips (the call that set it) — OK; if the postfix instead runs next frame it would be too late (the object is no longer updated). Recommended hook point: the same ManualUpdate call right after `IsStatic = true` (or a `Prefix/Postfix` that detects `_syncObject.IsStatic` and `_fallingStage == Landed`).
- **Return to active** (CONFIRMED): the only path is `UpdateRequiredHandler` subscribed to `OnUpdateRequired`. `SynchronizableObject._onUpdateRequired` is only read in `add_/remove_OnUpdateRequired`; no method ever invokes it (find_usages of the field = 2, both accessors). `SynchronizableObject.UpdateRequired()` has an empty body, its only caller is `TripwireSynchronizableObject.set_TripwireState`. So a static crate **never returns to the active list**, never gets `ManualUpdate` again, and (landed, `useGravity=false`, motion via transform) doesn't need physics again.
- **Physics need after landing**: landing contact detection uses `SyncObjectCollisionChecker.OnTriggerEnter` → `SynchronizableObject.CollisionEnter` → `ServerAirDrop.CollisionEnter` ⇒ **the fall needs Simulate ON** until `_fallingStage` leaves Fall/Parachute (trigger events). After `Landed` + `IsStatic` no code needs the rigidbody. Note `Landed` is reached after `RotateAfterDrop` coroutine (transform rotation, no physics). [INFERENCE: Unsupporting at IsStatic (≥ smoke duration after landing) is safe; unsupporting at `Landed` would also be safe but earlier.]
- **Re-Init of a pooled crate in the same raid** (CONFIRMED by absence): the crate never returns to the pool mid-raid (§3), and `TakeFromPool` is called per airdrop via `ObjectsFactory.CreateFromPool` (ServerPlane.AwaitContainerLoot) — a second airdrop gets a **different** pooled instance, with its own `ClientAirDrop` / own `ServerAirDrop` object (`new ServerAirDrop()` per `ClientAirDrop` ctor). Each crate registers exactly once (`Init` called once via `ServerPlane.AirdropReached`; `InitStaticObject` is a no-op for ServerAirDrop). So **no duplicate entries per rigidbody** in the normal flow; N airdrops in a raid ⇒ N entries, each needing its own Unsupport. Even if re-Init happened after a ReturnToPool, the stale entry would already have been purged (GO inactive) by `CheckRigidbodiesDone`. `ClientAirDrop.Init` additionally calls `SetActive(true)` before `OfflineServerLogic.Init` which also SetActive(true).
- A patch should call `UnsupportRigidbody` once per crate (but `UnsupportRigidbody` removes one entry; if a rigidbody could be double-registered, loop until count unchanged — not needed per the above, but cheap safety).

## 5. Other facts useful for the patch
- Also interesting: `ServerAirDrop.Init` uses default `quality = 1f`; `SupportRigidbody` raises `Simulation.Quality` (unused in `SmoothSimulate`, only in QualityControl mode) and `CheckRigidbodiesDone` resets `Quality = 0f` when the list is empty.
- `BaseTripwire.Init`/`ReturnToPool` pattern (Support after SetActive(false)) is the vanilla author's idiom, suggests BSG relies on auto-purge for inactive objects; they never Unsupport the airdrop because the crate only goes inactive at raid end.
- Not verified (outside budget): `SmokeGrenade` destroy path; `FlareCartridge`/`GrenadeCartridge`/`BeltDetachablePart` exit paths; which prefabs carry `WheelDrive`; `SmallPhysicsObject.TimeOfLife` values; whether Fika paths differ.
