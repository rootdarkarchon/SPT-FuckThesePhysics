- Creation (stock offline): `EFT.BaseLocalGame<T>.Run` state machine (`CG_Run.MoveNext`): `serverAirdropManager = new ServerAirdropManager(); .AirdropParameters = baseLocalGame.Location.airdropParameters; .Init(Singleton<AbstractGame>.Instance.GameType == EGameType.Offline); (Singleton<GameWorld>.Instance as ClientGameWorld).ClientSynchronizableObjectLogicProcessor.ServerAirdropManager = serverAirdropManager;`.
- Visual manager: `LevelSettings.OnPostLoadingScene()`: `new ClientAirdropManager()` -> `GameWorld.SynchronizableObjectLogicProcessor.Init(airdropManager)` then `.AirdropManager.Init(enableAirdrops:false)`.

## 2. Debug spawn design

### Options compared
A. **Direct client invocation (RECOMMENDED)**: `Singleton<GameWorld>.Instance.InitAirdrop(lootTemplateId, takeNearbyPoint, position)` on the main thread. Runs the exact real chain (plane flight, `InitContainerLoot` -> `/client/airdrop/loot`, parachute, landing). No server edits, immediate, repeatable. Requirements: `ServerAirdropManager` exists on this process (offline/Fika host only), map has `AirdropPoint`s, `CachedAirdropParameters != null`.
B. Force schedule via server config: edit `database/locations/<map>/base.json` `AirdropParameters` (`PlaneAirdropChance:1, PlaneAirdropMax:N, PlaneAirdropStartMin/Max:0-ish, MinPlayersCountToSpawnAirdrop:1, PlaneAirdropEnd` large). Real mechanism too, but needs server restart/DB edit, still timer-gated (`_nextSpawnAirdropTime` after Init, cooldown), not on-demand, and solo raid blocked by the min-players 6 unless set ≤1. No `airdrop.json` key controls chance. Good only for soak tests.
C. Flare gun: `ClientGameWorld.FlareSuccessEventHandler` path (needs `AmmoTemplate` with `FlareEventType.Airdrop`; waits `PlaneAirdropFlareWait`; spawns at nearest point to flare). Real but needs an airdrop flare item; can be simulated by calling `ServerAirdropManager.FlareSuccessEventHandler(profileId, pos, lootTemplateId)` (public) — then timer-gated by `PlaneAirdropFlareWait` and `_nextAirdropTimeByFlare`.
D. SPT debug tooling: none (spt-debugging has no airdrop code; `Player.DebugSpawnAirdrop` is an empty stub; Fika `CommandPacket.ECommandType.SpawnAirdrop` exists in the enum but `CommandPacket` has no usages/handler in Fika.Core.dll per find_usages=0 -> do not rely on it).
Also possible but inferior: bypass `ServerAirdropManager.ManualUpdate` timers by setting `_nextSpawnAirdropTime=0`, `_airdropsEnabled=true`; still random-chance gated.

### Exact call sequence (host/offline, main thread, in raid, after `GameWorld` + `ServerAirdropManager` ready)
1. Guard: `Singleton<GameWorld>.Instantiated`; `var gw = Singleton<GameWorld>.Instance as EFT.ClientGameWorld`; `var sam = gw?.ClientSynchronizableObjectLogicProcessor?.ServerAirdropManager` (type `EFT.Airdrop.ServerAirdropManager`); require `sam != null && sam.IsInited && sam._airdropPoints.Count + sam._deactivatedAirdropPoints.Count > 0 && sam.CachedAirdropParameters != null`. Else report "no airdrop points on this map / not host".
2. Optional force-enable: `sam._airdropsEnabled = true` (public field; in Fika host it is already true, in stock offline true when `GameType==Offline`).
3. Choose position: nearest drop point to the player: `gw.InitAirdrop(null, takeNearbyPoint: true, position: player.Transform.position)` (player = `GamePlayerOwner.MyPlayer`). Use `lootTemplateId = null` to let server roll the type (`airdrop.json` weightings); to pick a type pass a container template id (`_overrideLootTemplateId` semantic, `customAirdropMapping` keys such as `66da1b49099cf6adcc07a36b` = radar). NOTE: the plane needs the START point inside level bounds; if you get "out of level bounds" error in the log, retry with another point (call again; previous point was consumed/deactivated).
4. Do NOT also bump `_currentAirdropsCount`; calling `InitAirdrop` directly bypasses the counter/timers (so scheduled drops stay independent). Calling from a key handler in `Update()` is a main-thread call; do not call from async continuations on thread-pool (Unity objects).
5. Verify via BepInEx logger (EFT suppresses `Debug.Log`): poll `gw.ClientSynchronizableObjectLogicProcessor._activeSynchronizableObjects` for `AirplaneSynchronizableObject` then `AirdropSynchronizableObject` (`.IsInited`, `.IsStatic`).
Fail modes to handle: (a) `/client/airdrop/loot` fails after 3 retries -> plane vanishes silently (log `Debug.LogException` only) — server must be up; (b) loot item bundles load async (`LoadBundlesAndCreatePools`) before crate is lootable; (c) `TakeAirdropPoint` consumes/deactivates points within `AirdropPointDeactivateDistance`; repeated calls cycle once empty (`ActivateAirdropPoints`).
Harmony target candidates for the physics-fix part (public signatures, installed): `EFT.Airdrop.ServerAirDrop.ManualUpdate(float deltaTime)` (where `IsStatic` is set; postfix/transpile to also freeze: `SyncObjectRigidbody.isKinematic`/`detectCollisions`/`Physics`—see peer), `EFT.Airdrop.ServerAirDrop.CollisionEnter(Collider)`, `EFT.Airdrop.ClientAirDrop.ManualUpdate(float)`, `EFT.SynchronizableObjects.SynchronizableObjectLogicProcessor.RemoveNonActiveAndStaticObjects()`, `EFT.SynchronizableObjects.SynchronizableObject.IsStatic` field. Debug trigger needs no patch. Drop points: maps with chance>0 (bigmap, woods, shoreline, interchange, lighthouse, rezervbase, tarkovstreets, sandbox, sandbox_high, labyrinth) are expected to have `AirdropPoint`s; Factory/Labs/Terminal etc. have no `AirdropParameters` and (very likely) no points -> `TakeAirdropPoint` logs "There is no available AirdropPoints" and returns null [scene object presence UNVERIFIED; bundles not inspected].
